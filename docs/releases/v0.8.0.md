# SQLGuard Ninja v0.8.0: SQL injection prevention and defence in depth

## Security fixes (upgrade recommended)

* **SQLI-001 (critical, PostgreSQL, versions ≤ 0.7.0).** A query filtering on `@tenant_id` was accepted as tenant-pinned. PostgreSQL reads `@x` as `abs(x)`, so it returned every tenant's rows. Reproduced on PostgreSQL and fixed.
* **SQLI-002 (high, PostgreSQL).** `@column` hid a classified column from the privacy rules. Fixed.
* **SQLI-003 (medium, MySQL).** User and system variables (`@x`, `@@datadir`) are now denied.

## New: `execute_safe`

```python
rows = checkpoint.execute_safe(
    "SELECT o.id FROM orders o WHERE o.tenant_id = :tenant_id AND o.email = :email",
    ctx,
    PsycopgSafeExecutor(reader_dsn),
    params={"email": untrusted_email},
)
```

* Values are bound by the database driver: `sqlite3` natively, psycopg 3 server-side, and PyMySQL with its own client-side escaping. They never become SQL text.
* The template is authorized by the policy first. The tenant value comes only from the trusted request context; callers cannot supply or override it, in any letter case.
* Placeholders are found with the dialect tokenizer, so `:x` in literals or comments is ignored. Other markers (`?`, `%s`, `$1`, `@x`) are refused. Placeholder translation is verified reversible, so the executed statement is the validated one.
* Executors run read-only with timeouts and refuse sessions whose lexing differs from the guard (MySQL `sql_mode` and charset, PostgreSQL `standard_conforming_strings`).
* `safe_identifier` and `safe_order_by` handle dynamic identifiers through allowlists. Approved query templates are available for high-assurance applications.

## Evidence

The SQL injection regression suite runs against SQLite, PostgreSQL and MySQL 8.4 in CI; see `docs/development/SQLI_V080_RELEASE_GATE.md`.

This release reduces SQL injection risk. It does not guarantee immunity; read `docs/security/SQL_INJECTION_LIMITATIONS.md`.
